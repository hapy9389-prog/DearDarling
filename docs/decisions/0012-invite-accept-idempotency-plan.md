# 0012 — 초대 수락 결과 확인·안전한 재시도를 위한 멱등키 설계 (계획, 미구현)

날짜: 2026-09-13 (개정)
상태: **제안됨 — 검토 대기.** 이 문서는 설계만 기록한다. `apps/api` 코드·마이그레이션·
`.env`는 이 문서 작성으로 전혀 바뀌지 않았다.

## 배경

`apps/web`은 초대 수락(`POST /api/invites/:code/accept`) 응답이 미확정(5xx·202/503·
네트워크 오류)일 때 `realUser.coupleId` 재조회로 실제 연결 여부를 추정한다
([[SessionContext.tsx]]의 `realAcceptInvite`, 5xx를 확정 실패로 오분류하던 버그는 이미
고쳐 검증까지 끝냈다 — 이 문서와 무관하게 유지된다). 하지만 이 추정에는 근본적인 한계가
있다 — **coupleId 유무만으로는 "요청이 서버에 도달하지 않음" / "아직 처리 중" / "처리는
됐지만 응답만 유실됨"을 구분할 수 없다.**

이 문서는 클라이언트가 생성한 **수락 시도 식별 키(attempt key)** 를 서버가 결과와 함께
저장해, "이 특정 시도가 어떻게 됐는지"를 재조회 없이 직접 조회하고, 동일 키로 안전하게
재요청할 수 있게 하는 최소 설계를 제안한다. **새 키를 발급해 재시도하는 방식과, 시간 경과만
으로 실패를 확정하는 방식은 설계에서 명시적으로 배제한다.**

## 기존 방어 장치 (그대로 유지)

`apps/api/src/services/inviteService.ts`의 `acceptInvite`(184~269줄)는 이미 다음을
보장한다 — 아래 설계는 이를 감싸는 추가 레이어일 뿐, 대체가 아니다:
- `SELECT * FROM invites WHERE code = $1 FOR UPDATE` — 같은 코드의 동시 수락을 직렬화.
- 초대자·수락자 두 사용자 행을 **id 오름차순으로** `FOR UPDATE` — 교착상태 방지.
- `UPDATE users SET couple_id = $1 WHERE id IN (...) AND couple_id IS NULL` — 영향받은
  행 수가 2가 아니면 이미 연결된 것으로 보고 롤백(경합 시 이중 연결 방지).
- 트랜잭션 전체가 원자적으로 COMMIT/ROLLBACK — 부분 반영이 없다.
- 멱등키가 없는 기존 요청은 지금과 완전히 동일하게 동작한다(하위 호환) — 이 요구는 아래
  모든 절에서 반복해서 지킨다.

## 0. 구현 착수 전 선행 조건 (아직 준비되지 않음 — "Docker만 설치하면 그대로 실행 가능"이
아니다)

다음 실제 작업(로컬 통합 테스트 실행, 이어서 이 설계의 코드·마이그레이션 구현)에 들어가기
전에 **먼저 준비하고, 준비됐는지 직접 검증해야** 하는 항목들이다. 이번 문서 개정 시점에는
**아직 하나도 준비돼 있지 않다** — 검증되지 않은 안전성을 전제로 절차를 적지 않는다.

**(0-A) 실행 중인 API와 분리된 별도 작업 디렉터리**
이 맥에서 현재 실행 중인(또는 언제든 재시작될 수 있는) `apps/api`는 AWS 개발 DB에 연결돼
있다. `src/server.ts`의 `main()`은 `runMigrations(pool)`을 기동 직후 가장 먼저 실행하므로
(아래 "마이그레이션 자동 적용 위험" 참고), 이 설계를 구현할 마이그레이션 파일을 **그
프로세스가 지켜보는 디렉터리에 그대로 추가하면**, 이후 그 프로세스가 재시작될 때(정상
재시작뿐 아니라 크래시 후 자동 재시작 포함) 검토되지 않은 스키마 변경이 AWS 개발 DB에
자동으로 적용될 수 있다. 따라서:
- 구현은 **별도의 작업 디렉터리**(예: `git worktree add` 또는 완전히 별도의 로컬 클론)에서
  진행한다 — 지금 실행 중인 API 프로세스의 작업 디렉터리와 달라야 하고, 그 프로세스가
  `tsx watch`나 파일 변경 감지로 다시 읽어 들이는 경로가 아니어야 한다.
- 이 새 디렉터리에는 **실제 `.env`·`*.pem`·`*.local.json` 등 비밀 파일을 절대 복사하지
  않는다** — 아래 (0-B)가 이걸 전제로 한다.
- 새 마이그레이션 파일은 (0-B)·(0-C)로 준비된 격리 환경에서 로컬 테스트 DB로 전부
  검증한 **뒤에만** 원래 작업 디렉터리(AWS 연결 프로세스가 보는 곳)에 병합한다 — 병합
  자체가 곧 "AWS DB에도 적용"을 뜻하지 않도록, 병합 시점과 AWS DB 적용 시점을 분리하는
  절차는 아래 "마이그레이션 자동 적용 위험" 절에서 다룬다.

**(0-B) 실제 비밀값을 로드하지 않는 실행 경로**
`apps/api/src/config/loadDotEnv.ts`는 `process.cwd()`에 `.env`가 **존재하면 그대로 읽어**
아직 설정되지 않은 키(`COGNITO_*`, `SESSION_TOKEN_ENCRYPTION_KEY` 등 실제 비밀 포함)를
그 프로세스의 `process.env`로 채운다 — 파일 자체를 바꾸지는 않지만, 그 값이 프로세스
메모리에 올라간다는 사실 자체를 없애려면 **애초에 그 경로에 `.env`가 존재하지 않아야 한다.**
(0-A)의 별도 디렉터리에 `.env`를 복사하지 않으면 이 조건이 자연히 만족된다 — 다만 이번
문서 개정에서는 이걸 만들고 실제로 "거기서 `loadDotEnv()`가 아무 것도 하지 않는다"를 직접
확인하지 않았다. 이 확인이 되기 전까지는 통합 테스트를 실행하지 않는다. `TEST_DATABASE_URL`
을 어디서 읽든 **테스트 DB 접속 대상으로 실제로 쓰이는 값은 이것 하나뿐**이라는 점(§
"확인한 사실" 유지)과, 그 값이 로드되는 경로 자체에 다른 실제 비밀값이 함께 섞여 들어오지
않아야 한다는 점은 서로 다른 조건이며, 이 문서는 후자를 아직 "준비됨"으로 표시하지 않는다.

**(0-C) 오류 원문이 도구 실행 기록에 남지 않는 실행 방법**
`ensure-test-db.ts`·`migrate.ts`가 실패하면 `console.error(err)`로 오류 객체를 그대로
출력한다(§ "확인한 사실" 유지) — 이 출력은 명령을 실행하는 도구의 호출 결과 자체에 그대로
담긴다. **실행 뒤 그 결과를 사람이 요약해서 전달하는 것은 이미 발생한 원문 노출을 없던
일로 만들지 못한다** — 원문은 실행 시점에 이미 도구 호출 기록에 남는다. 따라서 이 스크립트들
(또는 이들을 부르는 `pnpm test`)을 실행하기 전에, 반드시:
- 표준출력·표준에러 전체를 **그 실행 명령 자체 안에서** 로컬 파일로 리다이렉트하고(예:
  스크래치 디렉터리의 로그 파일 하나로 합쳐 쓰기), 그 리다이렉트가 적용된 명령만 도구로
  실행한다 — 원문이 도구의 반환값에 담기지 않도록 실행 방식 자체를 바꾸는 것이지, 사후에
  걸러 말하는 것이 아니다.
- 그 로그 파일에서 통과/실패 여부를 판단할 때도 파일 전체를 그대로 출력하지 않고, vitest의
  요약 줄(`Test Files`, `Tests` 같은 고정 패턴)처럼 비밀값을 담을 수 없는 형태만 좁혀
  추출한다.
- 더 근본적인 해결(스크립트가 `src/logging/safeError.ts`의 `classifyError()`를 재사용해
  애초에 안전한 값만 출력하도록 고치는 것)은 코드 변경이라 이번 범위 밖이며, 다음 실제
  구현 라운드의 선행 작업으로 남긴다 — (0-C)의 리다이렉트 방식은 그때까지의 임시 완화책일
  뿐, 코드 자체를 고친 것은 아니다.

**이 세 가지가 실제로 준비되고, 준비된 상태 그대로 한 번 검증되기 전까지는 로컬 통합
테스트도, 이 설계의 코드 구현도 시작하지 않는다.**

## 1. 클라이언트: 시도별 식별 키 생성·보관

- 사용자가 "연결하기"를 누르는 시점에 `crypto.randomUUID()`로 `attemptKey`를 생성한다.
- 기존 `PendingInviteAccept` 레코드(`deardarling:web:v1:pending-invite-accept:<userId>`)에
  `attemptKey` 필드를 추가하고, **요청을 보내기 전에** 저장한다(현재도 `phase:'accepting'`을
  요청 전에 저장하는 것과 동일한 순서 — 이미 검증된 패턴을 그대로 확장).
- **pending 레코드가 이미 있으면(=이전 시도가 아직 미확정) 그 레코드에 저장된 attemptKey를
  그대로 재사용**한다. 코드나 날짜가 바뀌었다는 이유만으로 미확정 레코드를 지우고 새 키를
  만들지 않는다 — 새 키는 오직 pending 레코드가 없을 때(이전 시도가 확정 성공/확정 거절로
  이미 정리됐을 때)만 새로 생성한다(이미 구현된 "미확정 기록이 있으면 재진입 시 새 시도를
  막는" 화면 동작과 일치시키는 방향 — 이 계획 단계에서 그 화면 코드를 바꾸지는 않는다).
- `POST /accept` 요청에 `Idempotency-Key: <attemptKey>` 헤더로 실어 보낸다.
- **적용 순서**: 서버가 이 헤더를 지원·검증하고 아래 회귀 테스트가 전부 통과한 뒤에만 웹이
  실제로 헤더를 보내도록 바꾼다 — 서버가 아직 해석하지 않는 상태에서 웹이 먼저 보내기
  시작해도 헤더는 무시될 뿐 아무 멱등성 보장도 생기지 않는다.

## 2. DB: 새 테이블 (설계만, 미적용)

새 파일 `apps/api/migrations/0005_invite_accept_attempts.sql`(다음 순번) — 기존
`invites`·`users` 스키마는 컬럼 추가 없이 그대로 둔다:
```sql
CREATE TABLE invite_accept_attempts (
  id                       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id                  UUID NOT NULL REFERENCES users(id),
  attempt_key              TEXT NOT NULL,
  invite_code              TEXT NOT NULL,
  relationship_start_date  DATE,
  -- 'processing'은 이 행을 만든 트랜잭션이 아직 커밋하지 않은 동안만 존재하는 내부
  -- 전이값이다 — 커밋 전까지는 다른 커넥션에서 절대 관측되지 않는다(§4 참고).
  status                   TEXT NOT NULL CHECK (status IN ('processing', 'succeeded', 'rejected')),
  result_couple_id         UUID,
  reject_reason            TEXT,
  created_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, attempt_key)
);
```
`UNIQUE (user_id, attempt_key)`가 이 설계의 핵심 제약이다 — 같은 사용자가 같은 키로 보낸
요청은 항상 같은 행 하나로 수렴하고, `user_id`가 다르면 같은 키 문자열이어도 별개 행이라
소유권 분리가 스키마 수준에서 보장된다.

## 3. `POST /:code/accept` 확장 동작

`Idempotency-Key` 헤더가 있을 때만 아래 로직이 개입한다(없으면 기존 `acceptInvite(pool,
...)`를 지금과 완전히 동일하게 호출 — 하위 호환).

### (A) 동시 최초 요청 처리 — `INSERT ... ON CONFLICT DO NOTHING`

`SELECT ... FOR UPDATE`는 존재하지 않는 행을 잠글 수 없으므로 최초 시도 경쟁에는 쓸 수
없다. 대신:
```sql
INSERT INTO invite_accept_attempts
  (user_id, attempt_key, invite_code, relationship_start_date, status)
VALUES ($1,$2,$3,$4,'processing')
ON CONFLICT (user_id, attempt_key) DO NOTHING
RETURNING id
```
Postgres는 충돌 대상 행이 **아직 커밋되지 않은** 다른 트랜잭션의 것이면 그 트랜잭션이
끝날 때까지 이 INSERT를 자동으로 대기시킨 뒤 재평가한다(READ COMMITTED에서의 문서화된
동작 — § (C) 참고). 단순 유일성 위반을 곧바로 에러로 던지지 않는다:
- 행이 반환되면(경쟁에서 이겼다) 이 요청이 **처리 주체**가 되어 §(B)로 진행한다.
- 행이 반환되지 않으면(대기 후 실제로 충돌 확정 — 즉 이미 커밋된 결과가 존재) 같은
  트랜잭션 안에서 그 행을 `SELECT`해 `invite_code`/`relationship_start_date`가 이번
  요청과 같은지(§5 정규화 기준으로) 비교하고, 같으면 저장된 결과(성공/거절)를 그대로
  반환, 다르면 409 `attempt-key-conflict`로 거절한다. **단순 유일성 충돌이 500으로
  끝나는 경로는 없다** — 충돌은 "이미 처리됨"을 뜻하는 정상 분기다.

### (B) 연결 변경과 결과 기록의 원자성 — 같은 커넥션·같은 트랜잭션, SAVEPOINT

바깥에서 기존 `acceptInvite(pool, ...)`를 그대로 호출하는 방식은 그 함수가 **자기
`BEGIN`/`COMMIT`/`ROLLBACK`을 스스로 관리**하므로 원자성을 만들지 못한다 — 이 가정은
쓰지 않는다. 대신 `acceptInvite`의 잠금·검증·UPDATE 본문(현재 197~258줄)을
`acceptInviteLocked(client, code, accepterUserId, relationshipStartDate)`로 추출한다 —
**자기 `BEGIN`/`COMMIT`/`ROLLBACK`을 하지 않고, 호출자가 이미 연 트랜잭션의 `client`를
그대로 쓴다.** 기존 공개 `acceptInvite(pool, ...)`는 `BEGIN`→`acceptInviteLocked`
호출→`COMMIT`/`ROLLBACK`만 남겨 **완전히 동일한 외부 동작**을 유지한다(헤더 없는 기존
호출·기존 테스트는 무변경으로 그대로 통과해야 한다).

(A)에서 처리 주체가 된 경우:
```
SAVEPOINT before_accept
try:
  coupleId = acceptInviteLocked(client, code, accepterUserId, date)   -- 같은 client
  UPDATE invite_accept_attempts SET status='succeeded', result_couple_id=coupleId ...
  COMMIT                          -- 커플 연결 변경 + 성공 기록이 한 번에 커밋
catch InviteAcceptFailure as e:
  ROLLBACK TO SAVEPOINT before_accept   -- 커플/초대 관련 변경만 되돌림
  UPDATE invite_accept_attempts SET status='rejected', reject_reason=e.reason ...
  COMMIT                          -- 거절 "기록"만 남기고, 연결 변경은 이미 되돌아간 뒤 커밋
catch (그 외 예상 못한 오류: DB 접속 끊김 등):
  다시 던진다 -- 바깥 catch가 트랜잭션 전체를 ROLLBACK, invite_accept_attempts INSERT까지
                통째로 사라진다. "확정 거절"로 저장되지 않는다.
```
`InviteAcceptFailure`는 이미 `reason: InviteAcceptReason` 필드를 갖고 있어 그대로
재사용한다. 이 구조가 "예상된 업무상 거절은 연결 변경을 롤백하되 거절 결과는 보존, 예상
못한 오류는 확정 거절로 저장하지 않음"을 정확히 만든다.

### (C) 격리 수준 — READ COMMITTED를 명시적으로 지정, 잠금 대기 한도·타임아웃 흐름

이 새 멱등 경로의 트랜잭션은 시작 시 **명시적으로**
```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```
를 실행한다 — Postgres 기본값이 이미 READ COMMITTED이지만, (A)의 `INSERT ... ON CONFLICT`
블로킹·재평가 동작이 이 격리 수준에 의존하는 설계이므로 암묵적 기본값에 맡기지 않고 값을
직접 못박는다. **기존 헤더 없는 `acceptInvite`/`acceptInviteLocked` 경로에는 이 문장을
추가하지 않는다** — 기존 동작(암묵적 기본 격리 수준)을 그대로 유지해 회귀가 없게 한다.
- **잠금 대기 한도**: 무한정 대기를 막기 위해 이 새 트랜잭션에만 `SET LOCAL lock_timeout`
  (예: 수 초 단위, 정확한 값은 구현 시 부하 테스트로 정한다)을 추가로 건다.
- **시간 초과 시 처리**: `lock_timeout`(55P03) 또는 `statement_timeout`으로 대기가
  끊기면 그 시점까지 아무 것도 커밋되지 않으므로(자신이 처리 주체였다면 attempt 행 INSERT
  까지 함께) 트랜잭션 전체가 `ROLLBACK`된다. 이를 확정 실패로 응답하지 않는다 — 이미 웹
  쪽에서 고친 5xx-계열 처리와 동일한 **미확정** 계약으로 응답하고, 클라이언트는 상태
  조회(§4) 후 **같은 attemptKey로 안전하게 재시도**한다(새 키 발급도, 경과 시간만으로
  확정 실패 처리도 하지 않는다).

### (D) `processing` 가시성과 상태 조회 계약

한 트랜잭션 안에서 `processing` 삽입부터 최종 커밋까지 처리하므로, **다른 커넥션의 일반
조회(잠금 없는 `SELECT`)는 커밋되지 않은 `processing` 행을 절대 볼 수 없다**(MVCC). 따라서:
- **기본 설계(권장)**: 동시 재요청은 (A)의 `INSERT ... ON CONFLICT`가 자연히 첫 트랜잭션이
  끝날 때까지 **대기**시킨 뒤, 커밋된 최종 결과(성공/거절)를 그대로 반환한다. 별도의 즉시
  "processing" 응답 코드 경로가 필요 없다.
- `GET /api/invites/accept-attempts/:attemptKey`(본인 것만, `req.userId`로 스코프)는 커밋된
  `succeeded`/`rejected` 행이 있으면 그 결과를, **없으면 404 `{status:'not-found'}`**를
  반환한다. 이 404는 "확정 실패"가 아니라 **"아직 보이는(커밋된) 결과가 없음"**으로
  정의한다 — 시도가 실제로 없었던 경우, 지금 처리 중인 경우, 커밋 전에 중단된 경우가 모두
  이 하나의 관측 결과로 수렴하며, 클라이언트는 세 경우 모두 **같은 attemptKey로 안전하게
  `POST /accept`를 재요청**하는 것이 올바른 복구다.
- **즉시(비대기) 202 processing 응답이 제품상 꼭 필요한 경우에 한해**(기본 설계에는
  포함하지 않음): `pg_try_advisory_xact_lock(hashtextextended(user_id || ':' || attempt_key, 0))`
  로 같은 키에 대한 시도 여부를 논블로킹으로 먼저 확인하는 방법이 있다 — 잠금 획득 실패 시
  "지금 다른 요청이 처리 중"이 확실하므로 대기 없이 202를 즉시 반환할 수 있다(트랜잭션
  종료 시 잠금은 자동 해제). 별도 근거가 있는 선택 사항으로만 남기고 기본 설계로
  채택하지 않는다.

## 4. 동시 요청·서버 재시작에서의 정합성

- 한 트랜잭션 안에서 attempt 행 삽입·SAVEPOINT·최종 상태 갱신·커플 연결 UPDATE가 모두
  함께 COMMIT/ROLLBACK되므로, attempt 행 상태와 실제 커플 연결 상태가 어긋나는 경우가
  구조적으로 없다.
- 트랜잭션 커밋 전에 서버가 재시작/크래시하면 `'processing'` 행도 함께 사라진다 — 재시작
  후 같은 키로 재요청하면 "행 없음"으로 관측돼 깨끗하게 새로 처리된다. `'processing'`이
  실제로 관측 가능한 유일한 경우는 다른 트랜잭션이 **지금 실제로 진행 중**일 때뿐이며, 그때는
  (A)의 대기가 자연히 처리한다.
- 서로 다른 attempt_key로 같은 초대 코드를 동시에 수락 시도하는 경우는 attempt 락과 무관하게
  기존 invites/users `FOR UPDATE` 락이 그대로 직렬화·방어한다 — 이 설계는 그 위에 "같은
  사용자·같은 키"라는 한 겹을 추가할 뿐이다.

## 5. 키·정규화 기준

저장·비교 기준값은 라우트가 이미 검증해 만든 값을 그대로 쓴다 — `normalizeCode(code)`
(기존 `domain/invite.ts` 함수 재사용)와, `POST /:code/accept`가 이미 `isValidCalendarDate`
로 검증해 만든 `relationshipStartDate: string | null`(이미 `YYYY-MM-DD` 형식 또는
`null`) — 별도 정규화 로직을 새로 만들지 않는다.

## 6. 복구 흐름 — "기록 없음"은 확정 실패가 아니다

`GET .../accept-attempts/:attemptKey`가 404를 반환하면, 클라이언트는 **같은 attemptKey로
`POST /accept`를 그대로 재전송**한다. 요청이 서버에 도달한 적이 없었다면 정상적인 첫
시도로, 도달했지만 커밋 전에 중단됐다면 마찬가지로 새로 처리되며(트랜잭션이 롤백됐다면
정의상 아무 것도 반영되지 않았다), 실제로 성공/거절까지 커밋됐다면 애초에 404가 아니라
그 결과가 반환되므로 이 경로에 들어오지 않는다. 새 키를 발급해 재시도할 필요가 전혀 없다.

## 7. 기존 `/accept`와의 호환

`Idempotency-Key` 헤더는 선택이다. 헤더가 없는 요청은 `invite_accept_attempts`를 전혀
건드리지 않고 지금과 완전히 동일하게 동작한다 — 기존 클라이언트·기존 통합 테스트가 전부
그대로 통과해야 한다(회귀 없음). 웹 클라이언트가 헤더를 보내기 시작하는 시점은 §1의
"적용 순서"를 따른다(서버 지원·검증이 먼저).

## 8. 응답 계약 요약

| 상황 | POST /accept | GET 상태 조회 |
|---|---|---|
| 새 시도, 성공 | 200 `{ coupleId }` | 200 `{status:'succeeded', coupleId}` |
| 새 시도, 확정 거절 | 409 `{ error: reason }` | 200 `{status:'rejected', reason}` |
| 같은 키·같은 입력, 진행 중이던 요청 뒤 도착 | 대기 후 캐시된 결과 그대로 | (캐시된 결과) |
| 같은 키·다른 코드/날짜 | 409 `{error:'attempt-key-conflict'}` | (원래 입력 기준 유지) |
| 이 키로 시도한 커밋된 기록 없음(진행 전·진행 중·중단 전부 포함) | — | 404 `{status:'not-found'}` → 같은 키로 재요청 |
| 잠금 대기 시간 초과 | 미확정 응답(§(C)) | 위와 동일하게 "기록 없음"으로 관측될 수 있음 → 같은 키로 재요청 |

## 9. 마이그레이션 자동 적용 위험 — 향후 작업 순서 (중요)

`apps/api/src/server.ts`의 `main()`은 `loadEnv()`로 얻은 `env.databaseUrl`로 풀을 만든
**직후 가장 먼저** `await runMigrations(pool)`을 실행한다 — 즉 서버 프로세스가 재시작될
때마다(정상 배포뿐 아니라 크래시 후 자동 재시작, 재시작형 프로세스 매니저, 재부팅 등 의도치
않은 재시작 포함) 그 시점에 배포된 코드에 들어 있는 아직 적용 안 된 마이그레이션 파일을
자동으로, 별도 승인 없이 현재 `DATABASE_URL`이 가리키는 DB에 적용한다.

이 설계를 실제로 구현하는 다음 라운드에서는 아래 순서를 지킨다(이번 문서는 설계만 —
코드는 아직 없다):
1. §0의 선행 조건(별도 작업 디렉터리, 실제 `.env` 미복사, 로그 리다이렉트 준비)이 실제로
   갖춰지고 검증된 뒤에만 그 디렉터리에서 마이그레이션 파일과 관련 코드를 구현한다.
2. 로컬 테스트 DB로 §10의 회귀 테스트를 전부 통과시킨다 — AWS DB 근처에 이 코드를 두지
   않는다.
3. 로컬 검증이 끝나도, 이 마이그레이션이 포함된 코드를 AWS와 연결된 서버 프로세스가 실행
   중이거나 재시작될 수 있는 원래 작업 디렉터리에 곧바로 병합하지 않는다 — 병합 자체가
   그 프로세스의 다음 재시작에서 자동 적용으로 이어지는 것을 막기 위해서다.
4. 검토·승인 후, **의도적으로 별도 실행되는 절차**로만 AWS 개발 DB에 마이그레이션을
   적용한다 — 서버 재시작이 이 적용을 대신하게 두지 않는다.
5. 4번이 끝나 스키마가 이미 반영된 뒤에야 그 마이그레이션을 포함한 코드를 원래 작업
   디렉터리에 병합·배포한다(그 시점의 재시작은 `runMigrations`가 "이미 적용됨"만 확인하고
   지나간다).

## 10. 회귀 테스트 (구현 시 추가할 것)

- 성공 결과 재반환: 같은 키·같은 입력을 성공 커밋 후 재전송 → 동일 `coupleId`로 200,
  초대가 두 번 사용되지 않음(초대 status 불변 확인).
- 확정 거절 결과 재반환: 같은 키·같은 입력을 거절 커밋 후 재전송 → 동일 사유로 409, 애초에
  롤백됐던 커플/초대 상태가 여전히 원상태임을 확인.
- 동시 요청(진짜 동시): 같은 키·같은 입력을 첫 트랜잭션이 아직 커밋 전일 때 동시 전송 →
  (A)의 대기 동작으로 두 번째가 첫 번째 커밋을 기다렸다가 같은 결과 반환, `users.couple_id`
  는 정확히 한 번만 설정됨(이중 연결 없음), 500이 발생하지 않음. 다른 코드/날짜인 동시
  요청은 409 attempt-key-conflict, 기존 초대·사용자 행 불변.
- 커밋 전 중단: 트랜잭션이 끝나기 전에 커넥션이 끊기는 상황을 시뮬레이션 →
  `invite_accept_attempts`에 그 키의 행이 전혀 남지 않음 → 같은 키로 재요청 시 깨끗하게
  새로 처리되어 정확히 한 번 성공.
- 커밋 후 응답 유실: 커밋까지는 끝났지만 클라이언트로의 응답 전송에 실패하는 상황을
  시뮬레이션 → 같은 키로 재요청 시 저장된 성공 결과를 그대로 재반환(재실행 없음).
- 잠금 대기 시간 초과: `lock_timeout`을 짧게 설정한 테스트 전용 값으로 재현해, 시간 초과 시
  전체 롤백(attempt 행 포함 아무 것도 안 남음)·미확정 응답을 확인하고, 같은 키로 재요청 시
  (원인이 사라졌다면) 정상적으로 한 번만 처리됨을 확인.
- 상태 조회 권한: 다른 사용자가 남의 attemptKey를 조회 → 404(정보 노출 없음).
- 상태 조회 "기록 없음" 복구: 404 확인 후 같은 키로 POST 재요청 → 정상 처리되어 성공/거절로
  귀결.
- 헤더 없는 기존 요청 경로: 기존 `invites.test.ts` 전체가 리팩터 후에도 그대로 통과(회귀
  없음) — `acceptInviteLocked` 추출이 `acceptInvite`의 외부 동작을 바꾸지 않았음을 확인.

## 11. 참고 — 이번 계획에서 의도적으로 배제한 것

- **새 키 발급 재시도**: 재시도는 항상 같은 키를 재사용한다. 새 키는 사용자가 명시적으로
  다른 코드를 입력하는 등 "다른 시도"를 시작할 때만 생성한다.
- **시간 경과 기반 실패 확정**: `processing` 상태에 유효기간을 두고 자동으로 실패 처리하는
  방식은 넣지 않는다 — §4처럼 트랜잭션 원자성만으로 정합성이 보장되므로 타임아웃 추정이
  필요 없다. 오래된 `succeeded`/`rejected` 행의 보관 정책(청소 배치 등)은 이 설계와 무관한
  별도 주제로 남겨둔다.
