# 0002 — 대화 화면 검토 단계에서 지키는 동작 규칙

날짜: 2026-09-09 (최초 작성), 같은 날 2차 수정 — Codex 리뷰를 두 차례 반영

Codex가 코드를 직접 읽고 지적한 내용을 반영하며 정리한, 대화 화면(1단계)이 실제로 지키는 규칙이다. 화면만 만드는 단계라도 아래 규칙은 실제 서버가 생겼을 때도 유지되어야 하는 제품 규칙이므로, 여기 문서로 남겨 둔다.

**2차 수정 참고**: 2절("시나리오별 저장 공간")은 1차 작성 때와 방향이 달라졌다. 처음에는 모든 시나리오의 저장 공간을 분리했지만, "정상"과 "연결 끊김"은 연결 상태만 다를 뿐 같은 대화여야 한다는 지적을 반영해 **'빈 대화'만 예외로 두고 나머지는 하나의 저장 공간을 공유**하도록 다시 바꿨다. 아래 내용은 그 최종 상태를 기준으로 한다.

## 1. 전송 중·실패는 보낸 사람만 본다

`ChatMessage.status`가 `sending`/`failed`인 메시지는 서버에 저장된 적이 없는, 보낸 사람 쪽의 로컬(낙관적) 상태다. 실제 서버였다면 상대방에게 애초에 전달될 수 없다. 그래서 화면에 표시하기 직전에 `filterVisibleMessages(messages, viewerId)`([`apps/web/src/features/chat/chatTypes.ts`](../../apps/web/src/features/chat/chatTypes.ts))로 걸러낸다:

- 보낸 사람 본인: 모든 상태(`sending`/`failed`/`saved`)를 본다 — 재시도 버튼을 눌러야 하므로.
- 그 외(상대방): `saved`인 메시지만 본다.

`ChatPage`는 내부 상태(`messages`)는 그대로 두고, 렌더링 직전에만 이 필터를 적용한다. 코칭 근거로 넘기는 목록은 이 화면 표시용 필터와 별개로, `selectSavedMessages(messages)`로 저장 완료(`status: 'saved'`)된 메시지만 골라 넘긴다(자세한 이유는 6절).

검증: `chatTypes.test.ts`(순수 함수 유닛 테스트), `ChatPage.test.tsx`의 "전송 중이거나 실패한 메시지는 보낸 사람에게만 보이고..." 테스트(계정을 전환해 실제로 안 보이는지 확인).

## 2. 시나리오는 "같은 대화를 보는 관점"이지 별개의 대화가 아니다 — '빈 대화'만 예외

'정상'/'AI 준비 중'/'AI 장애'/'연결 끊김'은 대화 내용이 다른 게 아니라 **연결·AI 상태만 다른 같은 하나의 대화**다. 그래서 `chatService`는 이 네 시나리오에서 저장 공간을 공유한다(`couple:{coupleId}:messages`, [`apps/web/src/mocks/services/chatService.ts`](../../apps/web/src/mocks/services/chatService.ts)). '연결 끊김'에서 실패한 메시지는 '정상'으로 돌아오면 같은 대화 안에 그대로 남아 있고, 재시도하면 성공으로 바뀐다 — 시나리오를 바꾼다고 실패 기록이 사라지거나 별도 대화로 갈라지지 않는다.

**'빈 대화'만 다르게 동작한다.** 이 시나리오는 저장 공간을 아예 읽지도 쓰지도 않는다 — 그래서 **이 시나리오에 들어올 때마다(다른 시나리오에 있다가 다시 선택할 때마다) 항상 빈 화면으로 시작**한다. 같은 방문 중에 메시지를 보내면 화면에는 정상적으로 나타나지만(빈 대화 → 첫 메시지 전송 흐름을 검토할 수 있도록), 그 내용은 저장되지 않으므로 다른 시나리오로 넘어갔다가 돌아오면 다시 빈 화면이 된다. "빈 대화"를 "메시지를 한 번도 안 보낸 하나의 독립된 대화"로 유지하는 방식이 아니라 **"들어올 때마다 빈 상태를 재현하는 상태 미리보기"**로 정한 것이다 — 다른 모든 시나리오 버튼이 "누르면 정확히 이 상태를 보여준다"는 동일한 규칙을 따르기 때문에, '빈 대화'만 예외적으로 상태가 누적되면 오히려 일관성이 깨진다고 판단했다.

검증:

- `chatService.test.ts` — "정상/AI 준비 중/AI 장애/연결 끊김은 같은 하나의 대화(저장 공간)를 공유한다", "다른 시나리오에서 메시지를 보낸 뒤에도 빈 대화 시나리오는 그대로 비어 있다".
- `ChatPage.test.tsx` — "연결 끊김에서 실패한 메시지를 정상으로 돌아와 재전송하면 성공한다 — 같은 대화가 유지된다".

## 3. 코칭 영역 상태 우선순위: 분석 동의·철회 → AI 상태 → 코칭 숨기기 → 실제 제안

`ChatPage`의 코칭 영역 계산은 이 순서로 확인한다:

1. **분석 동의·철회** — 커플 분석이 비활성이면(한쪽이라도 철회) 다른 무엇보다 먼저 "분석 중단" 안내를 보여준다.
2. AI 상태(준비 중/장애)
3. 코칭 숨기기(본인 표시 설정)
4. 실제 코칭 제안 요청

동의·철회가 가장 먼저인 이유: "AI가 아직 준비 중이에요"라는 안내는 "곧 코칭을 받을 수 있다"는 기대를 주는데, 실제로는 분석 자체가 꺼져 있어서 준비 상태와 무관하게 코칭이 나오지 않는 상황이면 오해를 줄 수 있다. 그래서 AI 가동 상태와 무관하게 동의 여부부터 확인한다.

검증: `ChatPage.test.tsx`의 "AI 준비 중 시나리오여도 분석을 철회하면 분석 중단 안내가 먼저 보인다" 테스트.

## 4. 전송은 오직 버튼 클릭으로만 — Enter·한글 조합 확정 제외

`MessageInputBar`는 `<form onSubmit>`을 쓰지 않는다([`apps/web/src/features/chat/MessageInputBar.tsx`](../../apps/web/src/features/chat/MessageInputBar.tsx)). `<form>`이었다면 입력창에서 Enter를 누르거나 한글 조합을 Enter로 확정할 때 브라우저가 자동으로 제출했을 것이다. 전송 버튼은 `type="button"` + `onClick`으로만 동작하고, 입력창에는 어떤 키 입력 핸들러도 없다 — 그래서 Enter든, IME 조합 확정 중 발생하는 Enter든 애초에 전송으로 이어질 코드 경로가 없다.

검증: `ChatPage.test.tsx`의 "입력창에서 Enter를 눌러도..." / "한글 조합을 Enter로 확정해도..." 두 테스트(후자는 `compositionstart`/`compositionend`와 `isComposing: true`인 Enter keydown을 직접 흉내내 확인).

## 5. 전송 중에 시나리오를 바꿨을 때 — "같은 대화"면 결과를 반영하고, "빈 대화"는 방문이 다르면 버린다

메시지 전송·재시도는 700ms 지연 후에 완료된다. 그 사이에 리뷰어가 시나리오를 바꾸면 원래 요청은 백그라운드에서 진행되다가 나중에 완료된다. 이때 완료 결과를 지금 화면에 반영할지는 **시나리오 이름이 아니라 "같은 대화인지"로 판단**한다([`apps/web/src/features/chat/ChatPage.tsx`](../../apps/web/src/features/chat/ChatPage.tsx)).

- **'정상'/'AI 준비 중'/'AI 장애'/'연결 끊김'은 같은 하나의 대화**(2절)다. 전송 도중 이 넷 사이를 오가도(예: '정상'으로 보내다가 'AI 준비 중'으로 전환) 완료된 전송·재시도의 최종 상태(`saved`/`failed`)를 그대로 화면에 반영한다 — 시나리오 이름만 비교하면 이 경우에도 결과를 버려서, 저장은 됐는데 말풍선만 '전송 중'에 멈춰버리기 때문이다.
- **'빈 대화'는 저장 공간이 없어 들어올 때마다 새 방문**(2절)이다. 나갔다 다시 들어오면 이전 방문에서 진행 중이던 전송의 늦은 결과가 이번 빈 화면에 섞이면 안 된다. 그래서 '빈 대화'에 한해 **방문 번호(`visit`)까지 같을 때만** 결과를 반영한다.

정리하면 `ChatPage`는 요청 시작 시점의 "대화 식별값"(`reconcileToken` — '빈 대화'는 `empty#{방문번호}`, 나머지는 `main`)을 기억해 두고, 완료 시점의 값(`latestReconcileTokenRef.current`, 렌더마다 최신값으로 갱신)과 다르면 화면 상태(`messages`)에 반영하지 않는다. 저장 자체(`chatService`)는 그 요청이 속했던 시나리오의 저장 공간에 정상적으로 남는다 — 화면에 잘못 섞이는 것만 막을 뿐, 데이터를 잃지 않는다.

검증: `ChatPage.test.tsx`의
- "같은 대화 안에서 상태를 바꿔도(정상 → AI 준비 중) 전송의 최종 상태가 표시된다",
- "같은 대화 안에서 상태를 바꿔도 재시도의 최종 상태가 표시된다",
- "빈 대화를 나갔다 다시 들어오면 이전 방문의 늦은 전송 결과가 섞이지 않는다",
- "전송 중 시나리오를 바꾸면 이전 요청의 완료 결과가 새 화면에 섞이지 않는다"('정상' → '빈 대화'는 서로 다른 대화이므로 섞이지 않는 경우).

## 6. 코칭 분석 대상은 저장 완료된 메시지로 제한한다

`coachingService`에 근거로 넘기는 메시지 목록(`availableMessages`)은 `selectSavedMessages(messages)`로 걸러, `status: 'saved'`인 메시지만 포함한다([`apps/web/src/features/chat/chatTypes.ts`](../../apps/web/src/features/chat/chatTypes.ts), `ChatPage.tsx`). 전송 중이거나 실패한(아직 서버에 존재하지 않는 것과 같은) 메시지를 근거로 코칭을 만들면, 실패해서 사라질 수도 있는 내용을 근거 삼아 조언하게 되기 때문이다.

## 그 외 — 문구 정정

리뷰 도구(`DevPanel`)의 계정 전환 안내가 "초안도 계정별로 저장된다"처럼 읽혀 실제 동작(계정을 전환하면 초안은 저장되지 않고 그냥 비워짐)과 어긋났다. 초안을 굳이 계정별로 저장해서 복원하지 않는 이유는, 새 계정으로 전환한 화면에 이전 사람이 쓰던 문장이 잠깐이라도 남아있지 않게 하려는 의도가 더 크기 때문이다. 문구를 "초안은 사라진다(저장하지 않는다)"로 정정했다.
